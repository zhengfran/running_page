# Service-account calendar ownership vs. OAuth fallback for an unattended Garmin→Calendar sync

Research date: 2026-08-26. Google's docs on this topic carry explicit "Last updated" stamps; every dated claim below cites the stamp visible on the page at fetch time.

## Verdict

1. **Yes, qualified.** A service account (SA) CAN call `calendars.insert` and become the `dataOwner` of a new secondary calendar, using nothing but the SA's own credentials (self-signed JWT / OAuth2 client-credentials flow with the SA's private key) — no domain-wide delegation (DWD) and no Workspace license needed for the SA to own its **own** calendar. DWD is only required if you want the SA to *impersonate a human* and create calendars in that human's name — which is a different, unrelated need. Google's own reference page explicitly tells developers **not** to do this ("Don't use a service account for authentication... the service account is the data owner... data ownership cannot be transferred"), but that is a design recommendation about ownership transfer, not a technical block — and it doesn't apply to this design, which *wants* the SA to keep ownership permanently.

2. **Yes for the write-access mechanism, with one unavoidable manual, one-time step; qualified on the service-account-owner specifics.** `acl.insert` with `role: writer` grants genuine, native, fully bidirectional read/write access to the calendar — this is architecturally nothing like an ICS "subscribe by URL" feed (which is always read-only and pull-based); ACL-shared calendars are first-class calendars in the recipient's account. However, being *granted access* (ACL) and *appearing in the user's calendar list/UI* (`CalendarList`) are two separate, decoupled API collections per Google's own docs. Google's official consumer Help Center is explicit: after any calendar-level share, "They get an email. To find your calendar, they need to click the link in the email" / "To add your calendar, they must click the link in the email." That is a one-time human click, not a recurring re-auth — it does not violate the "zero manual re-authentication" requirement for the cron job itself, but it does mean the pipeline is not 100%-code-only at setup time. Whether that click-to-add flow behaves identically when the calendar owner is a service account (rather than a human) is **not explicitly documented** anywhere I could find — flagged explicitly below as a real gap, not inferred.

3. **No documented restriction currently blocks this.** The widely-cited 2023 "service accounts get 0 GB storage quota" change is a **Drive/Docs/Sheets/Slides/Photos/Gmail** storage-quota change, not a Calendar API change — Google's official storage-accounting page doesn't list Calendar among quota-consuming categories at all, and community reports independently confirm calendar entries don't count against the 15 GB storage pool. I found no dated 2023–2026 Google announcement, release note, or credible bug report saying service accounts can no longer create or own calendars. The only 2026-dated change found is a general Calendar API *usage-quota / future-billing* restructuring (requests-per-minute limits, planned billing later in 2026) that applies to all callers equally, not a service-account-specific ban.

4. a. **Confirmed: the 7-day refresh-token expiry applies only to apps whose OAuth consent screen has an External user type AND publishing status "Testing"** (and even then, not if the only scopes requested are basic profile/email/openid). Once the OAuth client is published with status "In production," this 7-day rule does not apply, whether or not the app has completed Google's verification review.
   b. Per Google's own "Refresh token expiration" list (verbatim, see below): user revokes access; refresh token unused for 6 months; password change **combined with Gmail scopes specifically** (a calendar-only-scoped token is not documented as being revoked by password change); the account exceeds 100 live refresh tokens for that OAuth client (oldest is silently invalidated — this cap explicitly does not apply to service accounts, though that's a separate credential type from the fallback OAuth-client path); a time-limited grant expiring; an admin restricting the scope (moot for a personal, non-Workspace account); GCP org session-control policies (moot for a personal account).
   c. **Yes, indefinitely, with one caveat.** Google's own verification-FAQ explicitly names "you are the only user of your app" as a legitimate case to stay unverified: the owner (and up to 99 more accounts, lifetime, non-resettable) can click through the "unverified app" warning once and keep using it. No forced re-verification deadline exists today for calendar's current sensitive-tier classification; Google's only stated future risk is that it "continuously re-evaluates" scope risk tiers and could reclassify a scope to a stricter tier later, in which case it gives advance email notice and a grace period before enforcement — not a currently-scheduled event for the calendar scope.

## 1. Service-account calendar creation and ownership

- `calendars.insert` reference (Last updated 2026-07-29): "Creates a secondary calendar, with the authenticated user becoming the data owner." Auth requires one of `https://www.googleapis.com/auth/calendar`, `.../calendar.app.created`, `.../calendar.calendars`. It then explicitly warns: *"We recommend to authenticate as the intended data owner of the calendar. You can use domain-wide delegation of authority to allow applications to act on behalf of a specific user. Don't use a service account for authentication."* And: using a service account means "the service account is the data owner, which can lead to unexpected behavior" including that "data ownership cannot be transferred."
  https://developers.google.com/workspace/calendar/api/v3/reference/calendars/insert
- The concepts guide (undated capture, current as of fetch) confirms the general ownership model: "Such calendars have a single data owner with the highest privileges, including the exclusive right to delete the calendar... The data owner is initially determined as the user who created the calendar, however the data ownership can be transferred in the Google Calendar UI." Nothing here says a service account is disallowed from being that data owner — the warning above is Google's *recommendation*, not an enforced technical restriction.
  https://developers.google.com/workspace/calendar/api/concepts/events-calendars
- Community corroboration (dated 2012, still linked from current Google search results as the top community answer, so treat as legacy/uncertain currency): a developer confirms a service account *can* be granted access to calendars and function normally once explicitly shared with; "outdated documentation" claiming Calendar API doesn't support service accounts was contradicted by working code.
  https://groups.google.com/g/google-calendar-api/c/MySzyAXq12Q
- **Reading for this design**: the "don't use a service account, ownership can't be transferred" warning is a caveat *against* the pattern of "SA creates a calendar for a human and later hands it over." It is not a statement that SA-owned calendars fail or get blocked — and in this design, permanent SA ownership is the intended outcome, so the warned-against downside is actually the desired behavior.

## 2. Sharing an SA-owned calendar to a personal Gmail with write access

- `acl.insert` reference (Last updated 2026-07-29): grants a `role` to a `scope` (`type: user`, `value: <email>`). `writer` = "Provides read and write access to the calendar... Provides read access to the calendar's ACLs." `sendNotifications` query param defaults to `True` ("Whether to send notifications about the calendar sharing change").
  https://developers.google.com/workspace/calendar/api/v3/reference/acl/insert
- Calendar sharing concepts page (Last updated 2026-08-12) documents the ACL role table (`none`/`freeBusyReader`/`reader`/`writerWithoutPrivateAccess`/`writer`/`owner`) and states ACL sharing is calendar-level, distinct from per-event invitations. It does **not** say anything about whether ACL grants alone make the calendar appear in the grantee's UI, and does **not** mention service accounts as owners or grantees at all — an explicit documentation silence, not an implied "no."
  https://developers.google.com/workspace/calendar/api/concepts/sharing
- `CalendarList` vs `Calendars` collections are explicitly distinct in the official concept doc: "The `CalendarList` is a collection of all calendar entries that a user has added to their list (shown in the left panel of the web UI). You can use it to add and remove existing calendars to or from the user's list." — i.e., ACL access ≠ list visibility.
  https://developers.google.com/workspace/calendar/api/concepts/events-calendars
- `calendarList.insert` (Last updated 2025-05-30) is the API call that inserts an *existing, already-accessible* calendar into `users/me/calendarList` — but it must be called **as the recipient**, which for a personal Gmail account with no domain-wide delegation means the recipient has to authorize a client themselves, or take the manual UI action below. A service account cannot call this on the human's behalf without impersonation, which (per the question's own premise, corroborated below) requires Workspace DWD and is unavailable for a personal @gmail.com account.
  https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/insert
- **Official consumer-facing Help Center article "Share your calendar"** (fetched verbatim, current) is the clearest statement of the human-facing flow, and applies regardless of whether sharing happened via the web UI or via the API (both ultimately create ACL rules + a notification email): *"They get an email. To find your calendar, they need to click the link in the email."* And in the numbered steps: *"The people you share your calendar with get an email. To add your calendar, they must click the link in the email."*
  https://support.google.com/calendar/answer/37082?hl=en
- **This means**: the design works, but is not zero-touch at *setup*. One-time, per new SA-owned calendar, the personal Gmail owner needs to click the sharing-notification email (or manually use "Other calendars → Subscribe to calendar" and paste the calendar's ID) to pin it into their `CalendarList`/UI. This is a UI action, not an OAuth grant — it does not expire and does not need repeating, so it is compatible with "zero manual re-authentication" for the recurring cron job itself, but it is a manual step the design must account for once per calendar.
- **Explicit gap**: I could not find any Google documentation, or any accessible community report, that specifically confirms or denies whether this "click the email link" flow behaves identically when the *sender/owner* is a service account rather than a human. One Google Issue Tracker thread titled **"Service Accounts don't accept automatically shared calendars"** (issue 148804709) is directly on-topic by title, but the page is behind Google's sign-in/CAPTCHA wall for both a direct fetch and a rendering-proxy fetch, so I could not read its body, comments, or resolution status. Based on the title alone, it appears to be about the *reverse* direction (a calendar being shared *to* a service account not auto-appearing for the SA), not about a human failing to receive a share *from* an SA-owned calendar — but I cannot confirm this from the title alone, and no other angle of the issue was accessible. **This is stated explicitly as unresolved rather than inferred**, per your instructions.
  https://issuetracker.google.com/issues/148804709 (inaccessible without a Google sign-in during this research session)
- Corroborating community answer (undated, but consistent with the above): sharing to a service account's own email works once the calendar owner explicitly adds the SA's email to the ACL; no auto-discovery happens either direction without an explicit ACL/CalendarList action.
  https://support.google.com/calendar/thread/94064838/how-do-i-share-a-calendar-with-a-service-account?hl=en (thread content largely inaccessible to automated fetch; treat with low confidence)

## 3. Current restrictions on service-account calendar creation/ownership

- The 2023 Workspace storage-quota change: "Starting June 1, 2023, newly created service accounts and existing service accounts using 0 GB will receive a 0 GB default storage quota... Exceptions for service accounts are not available. All data must be moved or deleted from service accounts by May 31, 2024." This is a **university-IT-summarized Workspace storage policy**, describing Drive/Docs-family storage specifically.
  https://it.wisc.edu/news/google-workspace-storage-quotas-start-jun-2023
- Google's own "What counts toward your Google Account storage" page (fetched verbatim) lists as quota-consuming: Photos backups, Gmail messages/attachments, Drive files, Meet recordings, and Docs/Sheets/Slides edited after 2021-06-01. **Google Calendar is not mentioned anywhere on this page, in either direction.**
  https://support.google.com/googleone/answer/9312312?hl=en
- Independent community confirmation: "Google Calendar entries on your calendar do not count against the data storage limit, but the emails you send and receive from Calendar, including those with attachments, do." (Google Calendar Community thread; treat as corroborating but not primary.)
  https://support.google.com/calendar/thread/172576434/does-data-stored-on-google-calendar-count-towards-the-15gb-storage-quota?hl=en
- Google Calendar API "Usage limits" guide (fetched in full): documents only *request-rate* quotas (10,000 req/min/project, 600 req/min/user/project, 1,000,000 req/day/project before future billing applies) and notes "As of May 1, 2026, the usage limits for this API were updated." No calendar-*creation* cap, no storage cap, and no service-account-specific prohibition anywhere on this page — only a note that SA calls are metered against a single account's per-minute quota unless you pass `quotaUser`.
  https://developers.google.com/workspace/calendar/api/guides/quota
- Google's 2026 cross-product "standardized model for agent tools and APIs" page confirms the May 1, 2026 quota changes apply project-wide (Gmail, Calendar, Drive APIs together) and that a billing requirement is coming "later in 2026, with at least 90 days' notice" for quota-increase requests — this is a rate-limit/billing change, not an access restriction on service-account calendar ownership.
  https://developers.google.com/workspace/tools-safety
- **Net assessment**: no primary source, dated announcement, or credible bug report found in this research says service accounts have lost, or will lose, the ability to create/own Calendar API calendars. The one real caveat is Google's own documented *recommendation* against SA-owned calendars (cited in §1) — a design guidance, not a deprecation.

## 4. OAuth 2.0 fallback path — refresh-token lifetime and viability

- Primary source, `developers.google.com/identity/protocols/oauth2` (Last updated 2026-05-26 UTC — 3 months before this research), fetched verbatim:

  > **Refresh token expiration** — You must write your code to anticipate the possibility that a granted refresh token might no longer work. A refresh token might stop working for one of these reasons:
  > - The user has revoked your app's access.
  > - The refresh token has not been used for six months.
  > - The user changed passwords and the refresh token contains Gmail scopes.
  > - The user account has exceeded a maximum number of granted (live) refresh tokens.
  > - The user granted time-based access to your app and the access expired.
  > - If an admin set any of the services requested in your app's scopes to Restricted (the error is `admin_policy_enforced`).
  > - For Google Cloud Platform APIs — the session length set by the admin could have been exceeded.
  > - A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of "Testing" is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile (through the userinfo.email, userinfo.profile, openid scopes, or their OpenID Connect equivalents).
  > - There is currently a limit of 100 refresh tokens per Google Account per OAuth 2.0 client ID. If the limit is reached, creating a new refresh token automatically invalidates the oldest refresh token without warning. This limit does not apply to service accounts.

  https://developers.google.com/identity/protocols/oauth2

- **(4a) Confirmed directly from the bullet above**: the 7-day expiry is scoped explicitly to "external user type" + "Testing" publishing status (with a narrow exception for basic-profile-only scopes, irrelevant here since Calendar is a sensitive scope). It says nothing about a shorter lifetime for "In production" + unverified — the enumerated reasons for a production token dying are the six/seven items above it, none of which is "unverified."
- **(4b)** Every other kill-switch is enumerated verbatim above: revocation, 6-month inactivity, password change *combined with Gmail scopes* (Calendar-only scopes are not listed as being affected by password change — worth flagging: this is what the primary doc says, but I did not find independent corroboration either confirming or refuting that Calendar-scoped tokens really do survive a password change; treat the "Gmail scopes only" qualifier as the literal, current doc text, medium confidence in practice), the 100-live-refresh-token-per-client cap (self-inflicted only if you re-run the auth flow repeatedly), and time-boxed grants/admin policy/GCP session control (all moot for a personal non-Workspace account with no admin).
- **(4c)** Google Cloud Platform Console Help, "Manage App Audience" (current, undated but reflects the modern Cloud Console UI): Testing apps are "limited to up to 100 test users" and "authorizations expire after seven days"; "In production" apps are "available to any user with a Google Account" once published, without the 7-day rule. Separately: unverified apps face "100 new users in total, after the app presents the unverified app screen... this quota applies across the project's entire lifetime and cannot be reset."
  https://support.google.com/cloud/answer/15549945?hl=en
  https://support.google.com/cloud/answer/7454865?hl=en
- Google's own sensitive-scope verification guidance explicitly carves out this exact use case: *"One use case is if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you."* Such an app can run "In production," unverified, indefinitely, with the owner (and anyone else who authorizes it) clicking through the standard "unverified app" warning once per authorization — consuming 1 of the lifetime 100-user cap, never revisited for a single-operator pipeline.
  https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification
- The only forward-looking risk documented: Google states it is "continuously re-evaluating the risk associated with user data access" and may reclassify scopes to a stricter tier later, in which case affected developers get "email notifications about the verification deadline" and a grace period before the unverified-app screen/cap kicks in harder. This is a general policy statement, not a scheduled event for the `calendar`/`calendar.events` scopes today.
  https://support.google.com/cloud/answer/7454865?hl=en
